# Notice Images to Supabase Storage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upload new notice photographs to a public Supabase Storage bucket and keep only their URLs in the database, so rows stay small and browsers cache the files, while notices already holding Base64 keep working untouched.

**Architecture:** One new server module, `server/services/notice-image-store.js`, owns everything about turning data URLs into bucket objects and back. It is created with a Supabase client or with `null`, and when given `null` every function is a passthrough — that single seam is what keeps the file-backed local mode working without a second code path. `server/server.js` calls it in three places (create, update, delete) and hands the thumbnail service a fetcher so the service can read a bucket URL as well as decode a data URL.

**Tech Stack:** Node 22, Express 4, `@supabase/supabase-js` (already a dependency, already constructed at `server/server.js:54`), `sharp`, Node's built-in test runner.

---

## Background an engineer needs before starting

Read `docs/superpowers/specs/2026-07-29-notice-images-to-storage-design.md` first. Beyond it:

- **The bucket already exists.** It is named `notice-images`, it is public, and it has no access policies. It needs none: the server authenticates with the service role key, which bypasses row level security, and public reads need no policy.
- **There is no Supabase locally.** `server/server.js:53` sets `useSupabase` from `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`; both are absent on a developer machine and set only on Render. Every test in this plan therefore drives a **fake** Supabase client. The real upload can only be confirmed after deploying.
- **Deletion is soft.** `softDeleteNotice` sets `is_deleted` and leaves the row. Nothing in the product restores it — the admin console never reads `is_deleted`. Removing the files is deliberate, not an oversight.
- **`js/` and `public/` are different things.** `public/` is generated by `npm run prepare:public`. This plan changes no browser code, so no rebuild is needed; if you find yourself editing `public/`, stop.
- **Tests live beside their subject.** Server behaviour goes in `tests/server-public-api.test.js` or a new server-side file; `tests/public-build.test.js` is for asserting on frontend source text and is not the place for this work.
- Run the full suite with `npm test`. It currently reports 178 passing and takes about 14 seconds.

```js
import crypto from 'node:crypto';

const BUCKET = 'notice-images';

// data URL에서 실제 바이트와 확장자를 꺼낸다. 그림이 아니면 null.
function decodeDataUrl(value) {
    const match = String(value || '').match(
        /^data:(image\/(avif|gif|jpe?g|png|webp));base64,([a-z0-9+/=\s]+)$/i
    );
    if (!match) return null;
    const body = Buffer.from(match[3], 'base64');
    if (body.length === 0) return null;
    const extension = match[2].toLowerCase() === 'jpeg' ? 'jpg' : match[2].toLowerCase();
    return { body, contentType: match[1].toLowerCase(), extension };
}

export function createNoticeImageStore({ supabase, supabaseUrl }) {
    const publicPrefix = supabaseUrl
        ? `${String(supabaseUrl).replace(/\/+$/, '')}/storage/v1/object/public/${BUCKET}/`
        : '';

    // 이 버킷이 가진 주소인지. 아니면 가져오지도, 지우지도 않는다.
    function isOwnedUrl(value) {
        return Boolean(publicPrefix) && String(value || '').startsWith(publicPrefix);
    }

    function keyFromUrl(value) {
        return isOwnedUrl(value) ? String(value).slice(publicPrefix.length) : '';
    }

    return {
        isOwnedUrl,

        // data URL만 버킷으로 올리고 주소로 바꾼다. 나머지는 그대로 둔다.
        // Supabase가 없으면(로컬 파일 모드) 전부 그대로 둔다.
        async persistImages(images) {
            const list = Array.isArray(images) ? images : [];
            if (!supabase) return list;

            const persisted = [];
            for (const image of list) {
                const decoded = decodeDataUrl(image);
                if (!decoded) {
                    persisted.push(image);
                    continue;
                }
                // 공지 id는 저장 뒤에야 생기므로 임의 이름을 쓰고, 지울 땐 주소에서 되짚는다.
                const key = `${crypto.randomUUID()}.${decoded.extension}`;
                const { error } = await supabase.storage.from(BUCKET).upload(key, decoded.body, {
                    contentType: decoded.contentType,
                    upsert: false
                });
                // 사진이 빠진 채 저장된 공지보다 저장 실패가 낫다.
                if (error) throw error;
                persisted.push(supabase.storage.from(BUCKET).getPublicUrl(key).data.publicUrl);
            }
            return persisted;
        },

        // 고아 파일이 남는 것보다 공지 삭제가 막히는 쪽이 나쁘다. 실패는 삼킨다.
        async removeImages(images) {
            if (!supabase) return;
            const keys = (Array.isArray(images) ? images : []).map(keyFromUrl).filter(Boolean);
            if (keys.length === 0) return;
            try {
                const { error } = await supabase.storage.from(BUCKET).remove(keys);
                if (error) console.warn('공지 이미지 삭제 실패:', error.message || error);
            } catch (error) {
                console.warn('공지 이미지 삭제 실패:', error.message || error);
            }
        }
    };
}
```

## Manual verification after deploy

Supabase is not configured locally, so none of the upload, delete, or fetch paths can run on this machine. After deploying, in the admin console:

1. Upload a notice with two photographs. It saves without a timeout.
2. In the Supabase dashboard, open Storage → `notice-images`. Two objects appear.
3. Open the notice on the public site. Both photographs display.
4. Open it a second time with the network panel recording. The images come from cache, and the detail response is a few kilobytes rather than megabytes.
5. Open a notice saved before this change. Its photographs still display.
6. Delete the notice from step 1. Its two objects disappear from the bucket.
